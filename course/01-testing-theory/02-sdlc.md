## SDLC — жизненный цикл разработки

**SDLC** (Software Development Life Cycle) — этапы, через которые проходит любая программа:

1. **Сбор и анализ требований** — что нужно сделать и зачем. Участвуют заказчик, аналитик, продакт-менеджер. QA уже здесь: ищет противоречия и «дыры» в требованиях.
2. **Проектирование** — как это будет устроено: архитектура, база данных, API.
3. **Разработка** — пишут код.
4. **Тестирование** — проверяют, что всё работает.
5. **Развёртывание (деплой)** — выкладывают на серверы для пользователей.
6. **Поддержка** — исправляют баги, выпускают обновления.

## Модели разработки

### Водопад (Waterfall)

Этапы идут строго друг за другом: пока не закончили требования, разработку не начинаем; тестирование — только в конце.

- ➕ Понятно, предсказуемо, хорошо документировано.
- ➖ Ошибку в требованиях находят в самом конце, когда исправлять дороже всего. Заказчик видит продукт только в финале.

Встречается в госзаказах, медицине, оборонке — где требования жёстко зафиксированы.

### V-модель

Водопад, у которого каждому этапу разработки соответствует уровень тестирования: требованиям — приёмочное тестирование, архитектуре — интеграционное, коду — модульное. Тесты **проектируют** параллельно с разработкой, а не в конце.

### Agile (гибкая разработка)

Продукт делают **короткими итерациями** (обычно 1–4 недели). В каждой итерации проходят все этапы: немного требований → немного кода → тестирование → выпуск. Заказчик видит результат каждые пару недель и может менять приоритеты.

Agile — это набор ценностей (Agile Manifesto, 2001), а конкретные способы работы — **Scrum** и **Kanban**.

### Scrum

Самый популярный фреймворк. Вы почти наверняка будете работать по нему.

| Термин | Что это |
|---|---|
| **Спринт** | Итерация фиксированной длины, обычно 2 недели |
| **Бэклог продукта** | Список всех задач, отсортированный по важности |
| **Product Owner** | Отвечает за то, *что* делаем и в каком порядке |
| **Scrum Master** | Следит за процессом, убирает препятствия |
| **Команда разработки** | Разработчики, QA, аналитики — все, кто делает продукт |
| **Планирование** | В начале спринта берут задачи из бэклога |
| **Дейли (daily standup)** | Ежедневная 15-минутная встреча: что сделал, что буду делать, что мешает |
| **Ревью (демо)** | В конце спринта показывают результат |
| **Ретроспектива** | Обсуждают, что улучшить в процессе |

### Kanban

Нет спринтов — задачи непрерывно движутся по доске с колонками: *To Do → In Progress → Code Review → Testing → Done*. Главное правило — ограничение числа задач в работе (WIP-лимит), чтобы ничего не застревало.

## STLC — жизненный цикл тестирования

У тестирования свои этапы:

1. **Анализ требований** — что и как можно проверить.
2. **Планирование** — стратегия, объём, сроки, окружения, риски (тест-план).
3. **Тест-дизайн** — придумываем проверки (чек-листы, тест-кейсы).
4. **Подготовка окружения** — стенд, тестовые данные, доступы.
5. **Выполнение** — прогоняем тесты, заводим баги.
6. **Завершение** — отчёт: что проверено, что нашли, какие риски остались.

## Окружения (стенды)

Программа живёт сразу в нескольких копиях:

| Окружение | Для чего |
|---|---|
| **local** | Компьютер разработчика или автоматизатора. У нас это QA Burger на `localhost:8081` |
| **dev** | Общий стенд разработки, там всё часто ломается |
| **test / QA / stage** | Стенд для тестирования, максимально похожий на боевой |
| **prod (production)** | «Боевой» стенд, где работают реальные пользователи |

Автотесты обычно умеют запускаться на любом стенде — меняется только адрес. Мы будем делать так же: адрес QA Burger будет браться из настроек (модуль 6).

## Чем занимается QA-автоматизатор в команде

Обычная неделя:

- Читает задачи следующего спринта, задаёт вопросы аналитику: «а что будет, если промокод истёк?»
- Пишет тест-кейсы и автотесты на новую функциональность.
- Чинит упавшие автотесты: разбирается, баг это в продукте или тест устарел.
- Смотрит результаты ночного прогона в CI.
- Заводит баг-репорты и проверяет исправления.
- Улучшает тестовый фреймворк.
