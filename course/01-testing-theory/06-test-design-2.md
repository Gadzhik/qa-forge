## Таблица решений

Подходит, когда результат зависит от **комбинации нескольких условий**. Составляем таблицу: строки — условия и действия, столбцы — правила (комбинации).

**Пример.** Можно ли отменить заказ в QA Burger?

| Условие / Правило | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| Пользователь — владелец или админ? | Да | Да | Да | Да | Нет |
| Статус NEW или PAYMENT_FAILED? | Да | Нет (PAID) | Нет (COOKING) | Нет (CANCELLED) | — |
| **Результат** | ✅ 200, CANCELLED | ❌ 409 | ❌ 409 | ❌ 409 | ❌ 404 |

Каждый столбец — один тест. Таблица гарантирует, что мы не забудем ни одной важной комбинации. Правило 2 ловит `BUG-405`, правило 5 — `BUG-204`.

> 💡 Если условий N и каждое да/нет, комбинаций 2ᴺ. При 5 условиях — 32. Часто многие комбинации невозможны или дают одинаковый результат — их **схлопывают** (как правило 5 выше: если пользователь чужой, статус уже неважен, поэтому там «—»).

## Диаграмма состояний и переходов

Подходит для объектов, у которых есть **жизненный цикл**: заказ, задача в трекере, банковская карта.

Заказ в QA Burger:

```text
                    оплата ок
         ┌──────┐ ───────────▶ ┌──────┐   кухня   ┌─────────┐  кухня  ┌───────┐
  create │ NEW  │              │ PAID │ ────────▶ │ COOKING │ ──────▶ │ READY │
  ──────▶│      │ ──────┐      └──────┘   (2 с)   └─────────┘  (3 с)  └───────┘
         └──────┘       │ оплата не прошла
            │  ▲        ▼
     отмена │  │  ┌────────────────┐
            │  └──│ PAYMENT_FAILED │  повторная оплата
            │     └────────────────┘
            ▼            │ отмена
       ┌───────────┐     │
       │ CANCELLED │◀────┘
       └───────────┘
```

Что тестируем:

1. **Все допустимые переходы** (каждую стрелку хотя бы раз): NEW→PAID, PAID→COOKING, COOKING→READY, NEW→PAYMENT_FAILED, PAYMENT_FAILED→PAID, NEW→CANCELLED, PAYMENT_FAILED→CANCELLED.
2. **Недопустимые переходы** — их система должна запрещать: PAID→CANCELLED (BUG-405), PAID→PAID (повторная оплата, BUG-502), CANCELLED→PAID, READY→CANCELLED.
3. **Полные пути**: NEW → PAID → COOKING → READY (BUG-501).

Недопустимые переходы — золотая жила багов: разработчики часто проверяют «можно ли», но забывают «нельзя ли».

## Попарное тестирование (pairwise)

Подходит, когда **много параметров**, у каждого несколько значений, и комбинаций слишком много.

**Пример.** UI-тест оформления заказа нужно проверить в:
- браузерах: Chrome, Firefox, Safari (3);
- ОС: Windows, macOS, Android (3);
- с промокодом и без (2);
- оплата: успешная, неуспешная (2).

Всех комбинаций: 3 × 3 × 2 × 2 = **36**.

**Наблюдение из практики:** подавляющее большинство багов вызывается значением одного параметра или **парой** параметров («в Safari на macOS не работает промокод»). Тройные сочетания редки.

Поэтому строят набор, где **каждая пара значений встречается хотя бы раз**. Для примера выше хватает ~9 тестов вместо 36. Такие наборы генерируют инструментами: **PICT** (от Microsoft, бесплатный, консольный), онлайн-генераторами pairwise.

Пример входного файла для PICT:

```text
Browser: Chrome, Firefox, Safari
OS:      Windows, macOS, Android
Promo:   Yes, No
Payment: Success, Fail
```

Команда `pict model.txt` выдаст таблицу из ~9 строк — это и есть набор тестов.

## Предугадывание ошибок (error guessing)

Опыт тестировщика: «здесь наверняка сломается». Типичные места:

- деление на ноль, пустые списки;
- округление денег (BUG-404);
- часовые пояса и переход через полночь, 29 февраля;
- двойной клик по кнопке «Оплатить» (BUG-502);
- одновременные действия с двух вкладок;
- очень длинные строки, эмодзи, спецсимволы;
- права доступа: что если подставить чужой id (BUG-204);
- что если внешний сервис не ответил (BUG-503).

## Какую технику когда применять

| Ситуация | Техника |
|---|---|
| Поле ввода с диапазоном или форматом | Классы эквивалентности + граничные значения |
| Результат зависит от комбинации условий | Таблица решений |
| У объекта есть статусы | Диаграмма состояний |
| Много независимых параметров | Pairwise |
| Всегда, в дополнение | Предугадывание ошибок |

```quiz
- q: Какую технику выбрать для проверки статусов заказа?
  options: [Граничные значения, Диаграмма состояний и переходов, Pairwise]
  answer: 1
- q: Какой переход у заказа должен быть ЗАПРЕЩЁН?
  options: ["NEW → PAID", "PAID → CANCELLED", "COOKING → READY"]
  answer: 1
- q: На чём основано попарное тестирование?
  options:
    - Большинство багов вызывается одним параметром или парой параметров
    - Тестировщики работают парами
    - Нужно проверить все комбинации
  answer: 0
- q: Результат зависит от трёх условий да/нет. Сколько максимум столбцов в таблице решений?
  options: ["3", "6", "8"]
  answer: 2
  explain: 2³ = 8.
- q: Какие места — классика для предугадывания ошибок? (несколько)
  options:
    - Округление денег
    - Двойной клик по кнопке оплаты
    - Цвет логотипа
    - Подстановка чужого id в адрес
  answer: [0, 1, 3]
```
