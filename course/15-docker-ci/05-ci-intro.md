## Определения

- **CI (Continuous Integration, непрерывная интеграция)** — каждое изменение кода автоматически собирается и проверяется тестами. Разработчик отправил код → через несколько минут видно, ничего ли не сломалось.
- **CD (Continuous Delivery/Deployment, непрерывная поставка/развёртывание)** — после успешных проверок изменение автоматически выкатывается на стенд (или в продакшен).

Набор автоматических шагов называется **пайплайн** (pipeline, «конвейер»):

```text
 push в git ──▶ сборка ──▶ юнит-тесты ──▶ деплой на test ──▶ API-тесты ──▶ UI smoke ──▶ деплой на stage ──▶ регресс ──▶ prod
                                            ▲                 ▲              ▲
                                       тут работают ваши автотесты
```

## Где здесь автоматизатор

Автотесты, которые запускаются только у вас на ноутбуке, приносят мало пользы. Ценность — когда они:
- запускаются **автоматически** на каждый Merge Request или ночью;
- **блокируют** слияние/выкатку, если что-то сломано (quality gate);
- публикуют **отчёт** (Allure), который видит вся команда;
- уведомляют в мессенджер о падениях.

Поэтому настройка запуска тестов в CI — обычная задача QA-автоматизатора.

## Инструменты

| Система | Где встречается | Как описывается пайплайн |
|---|---|---|
| **GitLab CI** | Очень часто в России (свои GitLab-серверы компаний) | `.gitlab-ci.yml` в репозитории |
| **GitHub Actions** | Открытые проекты, многие компании | `.github/workflows/*.yml` |
| **Jenkins** | Старый «тяжеловес», до сих пор очень распространён | `Jenkinsfile` (Groovy) или настройки в веб-интерфейсе |
| TeamCity, Azure DevOps, Bamboo | Встречаются реже | свои форматы |

Идеи везде одинаковы:
- **триггер** — когда запускать (push, MR, расписание, вручную с параметрами);
- **раннер/агент** — где выполнять (машина с Java, Docker-контейнер);
- **job/stage** — шаги: собрать, протестировать, построить отчёт;
- **артефакты** — что сохранить после (отчёты, логи, скриншоты);
- **переменные и секреты** — адреса стендов, пароли;
- **кэш** — чтобы не качать зависимости Maven каждый раз.

## Что важно для тестов в CI

1. **Headless-браузер** или удалённый Grid — экрана нет.
2. **Адрес стенда и секреты** — из переменных CI (урок 6.7), не из кода.
3. **Код возврата**: упавшие тесты должны делать job красным (Maven так и делает — урок 6.3). Не глушите ошибки `|| true`.
4. **Отчёт публикуется всегда**, даже если тесты упали (`when: always`, `if: always()`, `post { always { ... } }`).
5. **Время**: ограничивайте (timeout), параллельте, разделяйте smoke и полный регресс.
6. **Стабильность**: нестабильные тесты в CI быстро учат команду игнорировать красный цвет. Чините или изолируйте их.
