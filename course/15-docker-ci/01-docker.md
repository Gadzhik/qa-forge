С Docker вы уже встречались (уроки 11.5 и 13.3). Теперь разберёмся, как он устроен.

## Зачем Docker

«У меня работает, а на сервере — нет»: другая версия Java, нет нужной библиотеки, не та ОС. **Docker** упаковывает программу **вместе со всем окружением** (ОС-библиотеки, Java, настройки) в **образ**, который одинаково запускается где угодно: на вашем ноутбуке, у коллеги, на CI-сервере.

Для автоматизатора Docker — это:
- быстро поднять зависимости тестов (PostgreSQL, Kafka, WireMock, браузеры) одной командой;
- запускать тесты в одинаковом окружении на CI;
- поднимать тестируемое приложение изолированно для каждого прогона.

## Образ и контейнер

| Понятие | Что это | Аналогия |
|---|---|---|
| **Образ (image)** | Неизменяемый шаблон: файловая система + команда запуска. `postgres:16-alpine` | Установочный диск / класс |
| **Контейнер (container)** | Запущенный экземпляр образа со своими процессами и данными | Установленная программа / объект |
| **Реестр (registry)** | Хранилище образов: Docker Hub, GitLab Registry, Nexus | Maven Central для образов |
| **Тег** | Версия образа: `postgres:16-alpine`, `latest` | Версия библиотеки |
| **Том (volume)** | Данные вне контейнера, переживают его удаление | Внешний диск |

Контейнер — **не виртуальная машина**: он использует ядро ОС хозяина и стартует за секунды. (В Windows и macOS Docker Desktop держит маленькую Linux-машину, внутри которой и работают контейнеры.)

> ⚠️ Не используйте тег `latest` для того, от чего зависят тесты: сегодня `latest` — одна версия, завтра — другая, и тесты сломаются «сами». Фиксируйте версии (`postgres:16-alpine`, `apache/kafka:3.9.1`).

## Главные команды

```bash
docker run -d --name pg -p 55432:5432 -e POSTGRES_PASSWORD=secret postgres:16-alpine
```

- `docker run` — создать и запустить контейнер (если образа нет — скачать);
- `-d` — в фоне;
- `--name pg` — имя контейнера (иначе будет случайное);
- `-p 55432:5432` — пробросить порт: компьютер 55432 → контейнер 5432;
- `-e ИМЯ=значение` — переменная окружения внутри контейнера;
- `postgres:16-alpine` — образ и тег.

| Команда | Что делает |
|---|---|
| `docker ps` | работающие контейнеры (`-a` — включая остановленные) |
| `docker logs -f pg` | логи контейнера (`-f` — следить в реальном времени, Ctrl+C — выйти) |
| `docker exec -it pg sh` | открыть терминал внутри контейнера |
| `docker stop pg` / `docker start pg` | остановить / запустить |
| `docker rm pg` | удалить контейнер (`-f` — даже работающий) |
| `docker images` | скачанные образы |
| `docker pull image:tag` | скачать образ |
| `docker rmi image:tag` | удалить образ |
| `docker system prune` | удалить всё неиспользуемое (освободить место) |

## Dockerfile — рецепт образа

Образ QA Burger описан в `shop-app/Dockerfile`:

```dockerfile
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY target/shop-app-1.0.0-exec.jar app.jar
EXPOSE 8081
ENTRYPOINT ["java", "-jar", "app.jar"]
```

- **`FROM`** — базовый образ, от которого строим: Java 21 **JRE** (только для запуска — меньше по размеру, чем JDK);
- **`WORKDIR /app`** — рабочая папка внутри образа (создастся сама); дальнейшие команды выполняются в ней;
- **`COPY откуда куда`** — скопировать файл с компьютера (из **контекста сборки**) в образ;
- **`EXPOSE 8081`** — документация: «приложение слушает 8081». Порт наружу открывает только `-p` при запуске;
- **`ENTRYPOINT [...]`** — команда при старте контейнера.

Другие инструкции:
- `RUN команда` — выполнить при **сборке** (установить пакеты, собрать проект);
- `ENV ИМЯ=значение` — переменная окружения;
- `ARG` — параметр сборки;
- `CMD [...]` — команда по умолчанию (можно переопределить при запуске).

### Сборка и запуск

```bash
./mvnw -q -pl shop-app -am package -DskipTests
docker build -t qaburger:local shop-app
docker run -d --name shop -p 8081:8081 qaburger:local
```

- сначала собираем jar (Dockerfile его копирует);
- `docker build -t имя:тег папка` — собрать образ; папка `shop-app` — **контекст сборки**: только её содержимое доступно для `COPY`;
- запустить контейнер из своего образа.

### Слои и кэш

Каждая инструкция Dockerfile — **слой**. Docker кэширует слои: если инструкция и всё до неё не изменились — слой берётся из кэша. Поэтому сначала копируют то, что меняется редко (pom.xml, зависимости), потом — код. Файл **`.dockerignore`** (в корне курса) исключает из контекста `target/`, `.git/` и прочее — сборка быстрее, образ чище.
