## Зачем нужны ветки

В команде одновременно делают много задач: Аня пишет тесты корзины, Борис — тесты оплаты, а в `main` лежит стабильная версия, которую запускают каждую ночь. Если все будут коммитить прямо в `main` недоделанный код, ночной прогон будет постоянно падать.

**Ветка** — это отдельная линия истории. Вы создаёте ветку от `main`, спокойно работаете в ней, а когда закончили — **сливаете** (merge) обратно.

```text
main:      A───B───────────F (merge)
                \         /
feature/cart:    C───D───E
```

- `A`, `B` — коммиты в `main`;
- от `B` создали ветку `feature/cart`, в ней коммиты `C`, `D`, `E`;
- `F` — коммит слияния: изменения из ветки попали в `main`.

## Команды для веток

```bash
git branch
```

Показать список веток. Текущая отмечена `*`.

```bash
git switch -c feature/cart-tests
```

- `switch` — переключиться на ветку;
- `-c` (*create*) — сначала создать её;
- `feature/cart-tests` — имя. Принято писать префикс по типу задачи: `feature/...` (новое), `fix/...` (исправление), часто с номером задачи: `feature/QA-123-cart-tests`. Пробелы в именах веток нельзя.

> 💡 В старых статьях вместо `git switch` пишут `git checkout -b имя`. Это то же самое: `checkout` — старая универсальная команда, `switch` — новая, только для веток. Работают обе.

```bash
git switch main
```

Вернуться в ветку `main`. Файлы в папке **сразу изменятся** на версию из `main` — не пугайтесь, ваша работа сохранена в своей ветке (если вы её закоммитили!).

> ⚠️ Перед переключением веток закоммитьте или отложите изменения. Иначе Git либо откажется переключаться, либо перенесёт незакоммиченные правки в другую ветку. Отложить без коммита: `git stash` (спрятать), вернуть: `git stash pop`.

## Слияние (merge)

Закончили работу в ветке — переходим в ту, **куда** сливаем, и сливаем:

```bash
git switch main
git merge feature/cart-tests
```

`git merge X` — «влить ветку X в текущую».

Удалить ненужную ветку после слияния:

```bash
git branch -d feature/cart-tests
```

`-d` (*delete*) — удаляет только если ветка уже слита (защита от потери работы). `-D` — удалить принудительно.

## Конфликты

Конфликт возникает, когда в двух ветках **по-разному изменили одни и те же строки**, и Git не может сам решить, какую версию оставить.

Git остановит слияние и пометит место в файле:

```text
<<<<<<< HEAD
String baseUrl = "http://localhost:8081";
=======
String baseUrl = "http://test-stand:8081";
>>>>>>> feature/stand
```

- между `<<<<<<< HEAD` и `=======` — версия из текущей ветки;
- между `=======` и `>>>>>>> feature/stand` — версия из сливаемой ветки.

Чтобы разрешить конфликт:
1. Откройте файл, решите, какой вариант правильный (или совместите оба).
2. **Удалите** служебные строки `<<<<<<<`, `=======`, `>>>>>>>`.
3. Сохраните, затем `git add файл` и `git commit` (сообщение Git предложит сам).

> 💡 В IntelliJ IDEA конфликты удобно разрешать в окне **Merge**: три колонки — «ваша версия», «результат», «их версия», и стрелочки для переноса кусков. Его предлагают автоматически при конфликте (или **Git → Resolve Conflicts**).

## Практика

В своём репозитории `qa-notes` из прошлого урока:

```bash
git switch -c feature/theory
```

Создайте файл `theory.md` с конспектом 7 принципов тестирования, затем:

```bash
git add theory.md
git commit -m "Конспект принципов тестирования"
git switch main
ls
```

`ls` покажет, что `theory.md` в `main` **нет** — он живёт в ветке. Теперь сольём:

```bash
git merge feature/theory
ls
git log --oneline --graph --all
```

- после `merge` файл появился в `main`;
- `--graph` — нарисовать историю «ёлочкой»;
- `--all` — показать все ветки, а не только текущую.

> 🧪 **Попробуй сам: устрой конфликт.** Создайте ветку `a`, поменяйте первую строку `README.md`, закоммитьте. Вернитесь в `main`, создайте ветку `b`, поменяйте ту же строку иначе, закоммитьте. Влейте `a` в `main`, затем `b` в `main` — получите конфликт. Разрешите его.

## Rebase — для общего развития

Есть второй способ объединять ветки — `git rebase`. Он «переносит» ваши коммиты так, будто вы начали ветку от свежего `main`, — история получается прямой, без коммитов слияния. Во многих командах просят делать `git pull --rebase`. Главное правило: **не делайте rebase веток, которые уже отправили и с которыми работают другие** — это переписывает историю.
