До сих пор репозиторий жил только у вас на компьютере. Чтобы делиться кодом с командой (и показывать его работодателям), нужен **удалённый репозиторий** на сервере.

**GitHub** и **GitLab** — самые популярные сервисы для хранения Git-репозиториев. Плюс к хранению они дают:
- просмотр кода в браузере;
- **Pull Request / Merge Request** — обсуждение и ревью изменений перед слиянием;
- **CI/CD** — автоматический запуск тестов при каждом изменении (модуль 15);
- задачи (issues), вики и многое другое.

В российских компаниях очень распространён **GitLab** (часто — на собственных серверах компании), в международных — GitHub. Устроены они почти одинаково.

## Шаг 1. Регистрация

Зарегистрируйтесь на https://github.com (и/или https://gitlab.com). Имя пользователя выбирайте серьёзное — оно будет в ссылке на ваше портфолио: `github.com/anna-ivanova`.

## Шаг 2. SSH-ключ

Серверу нужно убедиться, что код отправляете именно вы. Удобнее всего — **SSH-ключ**.

**Как это работает.** Генерируется **пара ключей**:
- **приватный** (`id_ed25519`) — остаётся только у вас на компьютере, никому не показывается;
- **публичный** (`id_ed25519.pub`) — его можно показывать кому угодно; вы загружаете его на GitHub.

Математика устроена так, что подписать что-то можно только приватным ключом, а проверить подпись — публичным. Сервер проверяет подпись и понимает: «это Анна».

### Генерация ключа

Команда одинакова для всех ОС (в Windows выполняйте в PowerShell или Git Bash):

```bash
ssh-keygen -t ed25519 -C "anna@example.com"
```

- `ssh-keygen` — программа генерации ключей (входит в Windows 10+, macOS, Linux);
- `-t ed25519` (*type*) — алгоритм ключа. Ed25519 — современный, короткий и надёжный. В старых инструкциях встречается `-t rsa -b 4096` — тоже работает;
- `-C "..."` (*comment*) — подпись ключа, обычно почта; помогает понять, чей ключ.

Программа спросит:
1. `Enter file in which to save the key` — куда сохранить. Просто **Enter** (по умолчанию `~/.ssh/id_ed25519`).
2. `Enter passphrase` — пароль на сам ключ. Для учёбы можно оставить пустым (Enter дважды). На рабочем компьютере лучше задать.

### Копируем публичный ключ

```tabs
Windows: |
  ~~~powershell
  Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub | Set-Clipboard
  ~~~

  - `Get-Content` — прочитать файл;
  - `$env:USERPROFILE` — ваша домашняя папка (`C:\Users\Anna`);
  - `| Set-Clipboard` — передать содержимое в буфер обмена.
macOS: |
  ~~~bash
  pbcopy < ~/.ssh/id_ed25519.pub
  ~~~

  `pbcopy` копирует в буфер обмена то, что ему передали; `<` — передать содержимое файла на вход команде.
Linux: |
  ~~~bash
  cat ~/.ssh/id_ed25519.pub
  ~~~

  Выделите вывод мышкой и скопируйте (Ctrl+Shift+C в терминале).
```

> ⚠️ Копируйте файл с расширением **.pub**! Файл без расширения — приватный ключ, его никогда никуда не загружают.

### Добавляем ключ на сервер

- **GitHub:** аватарка → **Settings** → **SSH and GPG keys** → **New SSH key** → вставьте ключ → **Add**.
- **GitLab:** аватарка → **Edit profile** → **SSH Keys** → **Add new key**.

### Проверяем

```bash
ssh -T git@github.com
```

- `ssh` — программа защищённого подключения;
- `-T` — не открывать интерактивную сессию, просто проверить вход;
- `git@github.com` — пользователь `git` на сервере `github.com`.

Первый раз спросит `Are you sure you want to continue connecting?` — введите `yes` (это запоминание сервера). Успех: `Hi anna-ivanova! You've successfully authenticated`. Для GitLab: `ssh -T git@gitlab.com`.

## Шаг 3. Отправляем код на сервер

1. На GitHub: **+** → **New repository** → имя `qa-notes` → **Create repository** (без README, у нас уже есть).
2. GitHub покажет адрес вида `git@github.com:anna-ivanova/qa-notes.git`. В локальном репозитории:

```bash
git remote add origin git@github.com:anna-ivanova/qa-notes.git
git push -u origin main
```

- `git remote add origin АДРЕС` — запомнить удалённый репозиторий под именем `origin` («источник» — общепринятое имя для основного сервера);
- `git push` — отправить коммиты на сервер;
- `origin main` — куда (сервер `origin`) и какую ветку (`main`);
- `-u` (*upstream*) — связать локальную `main` с `origin/main`, чтобы дальше писать просто `git push` и `git pull`.

Обновите страницу на GitHub — там ваши файлы и история.

## Ежедневный цикл работы

```bash
git pull                                   # 1. забрать свежие изменения коллег
git switch -c feature/QA-42-payment-tests  # 2. ветка под задачу
# ... пишем тесты ...
git add .
git commit -m "QA-42: тесты повторной оплаты"
git push -u origin feature/QA-42-payment-tests   # 3. отправить ветку
# 4. на сайте создать Pull Request
```

- `git pull` = `git fetch` (скачать новые коммиты с сервера) + `git merge` (влить их в текущую ветку).

## Pull Request / Merge Request

**Pull Request** (GitHub) = **Merge Request** (GitLab) — запрос «пожалуйста, влейте мою ветку в main». В нём:
- видно все изменения (diff);
- коллеги оставляют комментарии к строкам кода — это **код-ревью**;
- автоматически запускаются тесты (CI);
- после одобрения кнопка **Merge** сливает ветку.

После `git push` новой ветки GitHub сам показывает кнопку **Compare & pull request**. Нажмите, опишите, что сделано, — **Create pull request**.

> 💡 Ревью автотестов — нормальная часть работы. Не обижайтесь на замечания: так учатся быстрее всего. И сами смотрите чужие PR — это отличный способ учиться.

## Клонирование

Чтобы получить копию существующего репозитория:

```bash
git clone git@github.com:anna-ivanova/qa-notes.git
```

Создаст папку `qa-notes` с полной историей и уже настроенным `origin`. Если ключа нет, можно клонировать публичный репозиторий по HTTPS: `git clone https://github.com/...`.
