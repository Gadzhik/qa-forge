## Зачем тестировщику базы данных

Всё, что делает пользователь, где-то сохраняется: заказы, корзины, пользователи. Это **база данных** (БД). Автоматизатор работает с ней постоянно:
- **проверяет побочные эффекты**: после `POST /api/orders` в базе появилась правильная запись, остаток товара уменьшился;
- **готовит данные**: быстро создать 100 заказов SQL-запросом, а не накликивать;
- **чистит** за тестами;
- **ищет причины багов**: API вернул странное — что лежит в базе?

На собеседованиях SQL спрашивают почти всегда: «напишите запрос, который…».

## Реляционная база

Самый распространённый вид БД — **реляционные**: данные хранятся в **таблицах**, а таблицы связаны между собой. Примеры: **PostgreSQL** (очень популярна), MySQL, Oracle, MS SQL Server, H2 (встраиваемая, для разработки и тестов).

Язык работы с ними — **SQL** (Structured Query Language), почти одинаковый для всех реляционных БД.

| Понятие | Что это | Аналог в Excel |
|---|---|---|
| **Таблица** | Набор однотипных записей | Лист |
| **Строка (запись)** | Один объект: один товар, один заказ | Строка |
| **Столбец (поле)** | Свойство: имя, цена | Столбец |
| **Тип столбца** | `INT`, `BIGINT`, `VARCHAR(100)`, `NUMERIC(10,2)`, `DATE`, `TIMESTAMP`, `BOOLEAN` | Формат ячейки |

## Ключи и связи

- **Первичный ключ (PRIMARY KEY)** — столбец, однозначно определяющий строку. Обычно `id`, который база заполняет сама (1, 2, 3...).
- **Внешний ключ (FOREIGN KEY, REFERENCES)** — столбец, ссылающийся на первичный ключ другой таблицы. Так таблицы связываются: заказ ссылается на пользователя (`orders.user_id → users.id`).
- **UNIQUE** — значения не повторяются (имя пользователя).
- **NOT NULL** — значение обязательно.

Типы связей:
- **один-ко-многим** — у пользователя много заказов, у заказа один пользователь. Самая частая;
- **многие-ко-многим** — у товара много заказов, в заказе много товаров. Реализуется **промежуточной таблицей** — у нас `order_items`;
- **один-к-одному** — редко.

## Схема QA Burger

Схема создаётся при запуске файлом `shop-app/src/main/resources/db/migration/V1__schema.sql` (инструмент **Flyway** — «миграции» базы).

```text
 users                    orders                       order_items
 ─────────                ─────────────                ──────────────
 id  PK  ◀────────────┐   id  PK  ◀──────────────┐     id  PK
 username UNIQUE      └── user_id  FK             └─── order_id  FK
 email                    status                       product_id
 password_hash            subtotal                     name
 role                     discount                     price
 created_at               total                        quantity
                          promo_code
     ▲                    created_at, updated_at
     │
 cart_items               products                     reviews
 ──────────               ─────────                    ─────────
 id  PK                   id  PK  ◀─────────────────── product_id  FK
 user_id  FK ─────────┐   name                         author
 product_id FK ───────┼─▶ description                  text
 quantity             │   price  NUMERIC(10,2)         rating
                      │   category                     created_at
 promo_codes          │   stock
 ───────────          │   emoji
 code  PK             │
 percent              └── (cart_items.user_id → users.id)
 valid_until
```

Наблюдения тестировщика:
- `order_items` хранит **копию** названия и цены товара на момент заказа — если цена товара потом изменится, старые заказы не «поплывут». Хорошая проверка!
- деньги — `NUMERIC(10,2)`: ровно 2 знака после запятой, без ошибок `double` (урок 3.2);
- пароль хранится **хешем** (`password_hash`), а не открытым текстом — тоже проверяется (заглянуть в базу и убедиться, что там не «user123»);
- `status` — строка (`NEW`, `PAID`...) — в базе можно найти «невозможные» статусы.

## Как заглянуть в базу QA Burger

**Без Docker** (база H2 внутри приложения):
- веб-консоль: http://localhost:8081/h2-console → JDBC URL `jdbc:h2:mem:shop`, User `sa`, пароль пустой → Connect;
- извне по JDBC (из тестов и DBeaver): `jdbc:h2:tcp://localhost:9093/mem:shop`, `sa`, пароль пустой.

**С Docker** (PostgreSQL, урок 11.5): `jdbc:postgresql://localhost:5432/qaburger`, пользователь и пароль `qaburger`.

> ⚠️ База H2 у QA Burger **в памяти**: при перезапуске приложения все данные возвращаются к начальным. Для тестов это удобно.

> 🧪 **Попробуй сам.** Откройте H2-консоль, выполните `SELECT * FROM products` и `SELECT * FROM users`. Оформите заказ на сайте и выполните `SELECT * FROM orders` и `SELECT * FROM order_items`.
