## Зачем брокер сообщений

Сервис заказов должен сообщить кухне, складу, сервису уведомлений и аналитике: «заказ №1 оплачен». Если он будет вызывать каждого по HTTP:
- он должен знать всех получателей (и меняться, когда появляется новый);
- если склад лежит — что делать с сообщением?
- если получателей десять — оплата будет ждать всех.

**Брокер сообщений** — посредник: отправитель кладёт **сообщение** в брокер и забывает; получатели читают его, когда готовы. Самые известные: **Apache Kafka** и **RabbitMQ**.

```text
 ┌──────────┐  ORDER_PAID   ┌──────────────────────┐   читает   ┌────────┐
 │ Заказы   │ ────────────▶ │  Kafka               │ ─────────▶ │ Кухня  │
 │(producer)│               │  топик qa-burger.    │ ─────────▶ │ Склад  │
 └──────────┘               │  orders              │ ─────────▶ │ Письма │
                            └──────────────────────┘            └────────┘
```

## Понятия Kafka

| Понятие | Что это |
|---|---|
| **Брокер** | Сервер Kafka. В кластере их несколько |
| **Топик (topic)** | Именованный «журнал» сообщений одной темы: `qa-burger.orders` |
| **Сообщение (record)** | Ключ + значение (обычно JSON) + заголовки + время |
| **Продюсер (producer)** | Тот, кто пишет сообщения в топик |
| **Консьюмер (consumer)** | Тот, кто читает сообщения |
| **Раздел (partition)** | Топик разбит на части для параллельности. У `qa-burger.orders` — 3 раздела |
| **Смещение (offset)** | Порядковый номер сообщения внутри раздела: 0, 1, 2... |
| **Группа консьюмеров (consumer group)** | Консьюмеры с одним `group.id` делят разделы между собой; каждая группа получает **все** сообщения независимо |

### Журнал, а не очередь

Ключевое отличие Kafka от классических очередей: сообщения **не удаляются** после чтения. Топик — это журнал, который хранит сообщения заданное время (например, 7 дней). Каждая группа консьюмеров сама помнит, до какого **offset** дочитала. Поэтому:
- новая группа может прочитать историю с начала (`auto.offset.reset=earliest`) или только новое (`latest`);
- тест может прочитать события, не мешая настоящим потребителям (своя группа или чтение без группы).

### Ключ и порядок

Сообщения с **одинаковым ключом** попадают в **один раздел** и читаются строго **по порядку**. QA Burger использует как ключ id заказа — поэтому события одного заказа идут по порядку: CREATED → PAID → COOKING → READY. Между разными разделами порядок не гарантирован.

### Группы и масштабирование

```text
 топик (3 раздела)         группа "kitchen"
 ┌───────────┐            ┌─────────────┐
 │ раздел 0  │──────────▶ │ consumer A  │
 │ раздел 1  │──────────▶ │             │
 │ раздел 2  │──────────▶ │ consumer B  │
 └───────────┘            └─────────────┘
```

Внутри группы каждый раздел читает ровно один консьюмер. Запустили вторую кухню — Kafka перераспределит разделы (**rebalance**), и заказы будут обрабатываться вдвое быстрее.

### Гарантии доставки

- **at most once** — не больше одного раза (может потеряться);
- **at least once** — хотя бы раз (может прийти **дважды**!) — самый частый режим;
- **exactly once** — ровно один раз (сложно, в особых настройках).

Отсюда важная проверка для QA: **идемпотентность** обработчика — дубликат события не должен приводить к двойному действию (двойному списанию, двум письмам).

## Kafka в QA Burger

- Профиль `kafka` (входит в `docker`): `KafkaEventPublisher` пишет события в топик `qa-burger.orders`, ключ — id заказа, значение — JSON:

```json
{"type":"ORDER_PAID","orderId":1,"userId":2,"total":289.90,"status":"PAID","timestamp":"2024-05-12T12:01:16Z"}
```

- Кухня — консьюмер в группе `kitchen` (`@KafkaListener` в том же классе), получает ORDER_PAID и меняет статус.
- Без Kafka (обычный запуск) события передаются кухне внутри приложения — поэтому все уроки до 13.3 работают без Docker.

## Что тестируют в системах с Kafka

- **Продюсер**: после действия в топик ушло сообщение правильного формата (контракт!), с правильным ключом и данными.
- **Консьюмер**: если положить сообщение в топик, сервис правильно его обработает (статус изменился, письмо отправлено). Тест сам становится продюсером.
- **Порядок**, **дубликаты**, **некорректные сообщения** (битый JSON не должен «ронять» консьюмера навсегда — такие отправляют в отдельный «топик ошибок», DLQ).
- **Задержки**: всё асинхронно → Awaitility.
