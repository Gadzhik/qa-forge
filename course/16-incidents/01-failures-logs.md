Утро. Ночной прогон: 37 упавших тестов из 1200. Работа автоматизатора — быстро понять по каждому: **баг в продукте, проблема окружения или ошибка в тесте**. От этого зависит, что делать дальше: заводить баг, писать DevOps или чинить тест.

## Алгоритм разбора

1. **Сгруппируйте.** 30 тестов упали с одинаковой ошибкой `Connection refused`? Это одна проблема (стенд лежал), а не 30. В Allure — вкладка **Categories**.
2. **Прочитайте сообщение об ошибке** — первую строку. Чаще всего ответ уже там.
3. **Найдите место в тесте** — первую строку стектрейса из вашего пакета (урок 5.1).
4. **Посмотрите вложения**: запрос и ответ API, скриншот, HTML страницы, шаг, на котором упало.
5. **Воспроизведите** — запустите тест один локально. Падает стабильно → вероятно, баг или устаревший тест. Проходит → нестабильность (урок 16.2).
6. **Посмотрите логи приложения** в момент падения.
7. **Сделайте вывод** и действуйте: баг-репорт, задача на тест, сообщение про стенд.

## Типы ошибок и что они значат

| Сообщение | Чаще всего означает |
|---|---|
| `expected: <X> but was: <Y>` (`AssertionFailedError`) | Поведение отличается от ожидания: **баг** или **устаревшая проверка** |
| `Expected status code <200> but was <500>` | Сервер упал → смотреть логи сервера; почти всегда **баг** |
| `Expected status code <200> but was <401>` | Токен не передан/истёк → проблема **теста** или авторизации стенда |
| `Connection refused`, `UnknownHostException` | Приложение недоступно → **окружение** |
| `SocketTimeoutException`, `Read timed out` | Сервер не ответил вовремя → нагрузка на стенде или реальная деградация |
| `NoSuchElementException`, `Element not found` (Selenide) | Изменилась вёрстка, элемент не успел появиться, или он в iframe |
| `StaleElementReferenceException` | Страница перерисовалась → **ожидания в тесте** |
| `ElementClickInterceptedException` | Элемент закрыт другим (баннер, меню) → баг вёрстки или тест |
| `ConditionTimeoutException` (Awaitility) | Асинхронное событие не наступило за время → баг или медленный стенд |
| `NullPointerException` в коде теста | Тест получил не те данные (поле отсутствует в ответе) → смотреть ответ |
| `UnrecognizedPropertyException` (Jackson) | В ответе API новое поле → изменился контракт |
| `SessionNotCreatedException` | Не стартовал браузер → окружение (версия браузера, Grid) |

## Читаем сообщения библиотек

**AssertJ:**

```text
org.opentest4j.AssertionFailedError: [итог корзины]
expected: 869.70
 but was: 289.90
```

`[...]` — описание из `as(...)`. Понятно, что не учлось количество (BUG-304).

**REST Assured:**

```text
java.lang.AssertionError: 1 expectation failed.
JSON path total doesn't match.
Expected: <869.7F>
  Actual: <289.9F>
```

**Selenide:**

```text
Element should have exact text "3" {[data-testid=cart-count]}
Element: '<span class="cart-count" data-testid="cart-count">1</span>'
Actual value: exact text="1"
Screenshot: file:/.../build/reports/tests/1715515275.png
Timeout: 4 s.
```

Элемент **найден**, но текст другой → это не проблема локатора, это поведение (BUG-701).

## Логи приложения

Лог — журнал событий, который пишет программа. Строка лога QA Burger:

```text
2026-10-14T09:33:49.441+02:00  INFO 107505 --- [qa-burger] [nio-8092-exec-5] r.q.shop.events.KafkaEventPublisher : kafka -> qa-burger.orders ORDER_CREATED order=1
```

| Часть | Значение |
|---|---|
| `2026-10-14T09:33:49.441+02:00` | время (с часовым поясом!) |
| `INFO` | **уровень** |
| `107505` | id процесса |
| `[nio-8092-exec-5]` | поток (запрос обрабатывал поток Tomcat №5) |
| `r.q.shop.events.KafkaEventPublisher` | **логгер** — какой класс написал |
| после `:` | сообщение |

Уровни: **TRACE < DEBUG < INFO < WARN < ERROR**. На стендах обычно пишут от INFO и выше. Ищите **ERROR** и **WARN** около времени падения теста.

Где логи QA Burger:
- файл `logs/shop-app.log` (обычный запуск) или окно/терминал, где запущено приложение;
- последние строки по HTTP: http://localhost:8081/api/debug/logs?lines=200 — удобно прикладывать к отчёту прямо из теста;
- в Docker: `docker logs qaburger-app`.

Поиск по логу:

```tabs
macOS / Linux: |
  ~~~bash
  grep -n "ERROR" logs/shop-app.log | tail -20
  grep -n "order=42" logs/shop-app.log
  grep -B 3 -A 20 "Exception" logs/shop-app.log | less
  ~~~

  - `-n` — номера строк; `tail -20` — последние 20 совпадений;
  - `-B 3 -A 20` — показать 3 строки до и 20 после совпадения (стектрейс);
  - `less` — постраничный просмотр (выход — `q`).
Windows (PowerShell): |
  ~~~powershell
  Select-String -Path logs\shop-app.log -Pattern "ERROR" | Select-Object -Last 20
  Select-String -Path logs\shop-app.log -Pattern "order=42"
  Select-String -Path logs\shop-app.log -Pattern "Exception" -Context 3,20
  ~~~
```

### Связать тест и лог

Хороший приём — **идентификатор запроса**: тест отправляет заголовок `X-Request-Id: <uuid>` (фильтр REST Assured, урок 9.5), приложение пишет его в каждую строку лога. Тогда по id из отчёта находится ровно нужный кусок лога. В микросервисах ту же роль играет **trace id** (урок 16.3).

Без id — ищите по **времени** (время падения есть в Allure и surefire-отчётах — учитывайте часовой пояс) и по **данным теста** (номер заказа, имя пользователя).
