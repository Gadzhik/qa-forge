В больших системах QA всё чаще участвует в разборе **инцидентов** — сбоев на стендах и в продакшене: помогает воспроизвести, найти первопричину, пишет автотест, чтобы ошибка не повторилась. Для этого нужно понимать инструменты **наблюдаемости** (observability).

## Три столпа наблюдаемости

| | Что это | Вопрос | Инструменты |
|---|---|---|---|
| **Метрики** | Числа во времени: запросов в секунду, доля ошибок, время ответа, память | **Что** и **когда** сломалось? | Prometheus + **Grafana** |
| **Логи** | Текстовые события сервисов | **Что именно** происходило? | **Loki**, ELK (Elasticsearch + Kibana), OpenSearch |
| **Трейсы** | Путь одного запроса через все сервисы с длительностями | **Где** тормозит/падает? | **Jaeger**, Tempo, Zipkin (OpenTelemetry) |

### Метрики

Классический набор для любого сервиса — **RED**:
- **R**ate — запросов в секунду;
- **E**rrors — доля ошибок (5xx);
- **D**uration — время ответа, обычно перцентили **p50/p95/p99** («95% запросов быстрее X мс»).

На графике в Grafana видно: в 03:14 доля ошибок оплаты выросла с 0% до 40%, а p99 времени ответа — с 200 мс до 5 с. **Алерт** (оповещение) срабатывает по правилу: «ошибок > 5% дольше 5 минут» → сообщение дежурному.

### Логи в централизованной системе

Вместо `grep` на каждом сервере — общий поиск по логам всех сервисов. Пример запроса в Loki (язык **LogQL**):

```text
{app="qa-burger", env="stage"} |= "ERROR" |= "payment"
```

- `{...}` — метки потока: приложение, стенд;
- `|= "текст"` — строка содержит текст.

### Трейсы

Запрос пользователя «оплатить» проходит: шлюз → сервис заказов → платёжный сервис → банк. **Trace** — дерево **спанов** (span — один участок работы с началом, концом, сервисом и атрибутами). В Jaeger видно:

```text
POST /api/orders/42/pay                         5 120 мс  ❗
 ├─ orders-service: load order                      12 мс
 ├─ orders-service → payment-service: charge     5 090 мс  ❗
 │   └─ payment-service → bank: POST /payments   5 000 мс  timeout
 └─ orders-service: save status PAYMENT_FAILED       8 мс
```

Сразу видно, где время и где ошибка: таймаут банка. **trace id** пишется и в логи — по нему находятся все строки всех сервисов для этого запроса.

## Kubernetes — минимум для QA

Многие стенды работают в **Kubernetes** (k8s): приложения — в контейнерах (**pod**), управление — командой **kubectl**. Полезные команды (если у вас есть доступ к тестовому кластеру):

```bash
kubectl get pods -n stage                      # список подов в пространстве stage (видно рестарты и статус)
kubectl describe pod orders-7d9f -n stage      # подробности: события, причина перезапуска (OOMKilled!)
kubectl logs orders-7d9f -n stage --since=15m  # логи пода за 15 минут
kubectl logs orders-7d9f -n stage --previous   # логи упавшего предыдущего экземпляра
kubectl rollout history deployment/orders -n stage   # история выкаток
```

- `-n stage` — **namespace** (пространство имён, часто = стенд);
- `RESTARTS` больше нуля и статус `CrashLoopBackOff` — приложение падает при старте;
- `OOMKilled` — превысило лимит памяти.

## Разбор инцидента: порядок действий

1. **Симптом**: что видит пользователь/алерт (растут ошибки оплаты).
2. **Масштаб**: всех затронуло или часть (один стенд, один тип карты)?
3. **Когда началось** (метрики) и **что изменилось** в это время: деплой (история в GitLab/ArgoCD, `rollout history`), изменение конфигурации, нагрузка, внешний сервис.
4. **Где** (трейсы) и **что именно** (логи с trace id).
5. **Гипотеза → проверка**: воспроизвести на тестовом стенде (тут пригодятся ваши автотесты и WireMock для имитации сбоя внешнего сервиса).
6. **Устранение** (откат, исправление) и **проверка** — метрики вернулись в норму.
7. **Постмортем** — разбор без поиска виноватых: хронология, первопричина, что сделать, чтобы не повторилось. Частый пункт: «добавить автотест на сценарий» — это ваша часть.

> 💡 «Первопричина» — не «упал сервис», а то, почему он упал: «после релиза 2.14 клиент платёжки создавался на каждый запрос, кончились соединения». Спрашивайте «почему?» несколько раз подряд (техника «5 почему»).
