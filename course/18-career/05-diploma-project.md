Дипломный проект — **ваш собственный** тестовый фреймворк для QA Burger в отдельном репозитории на GitHub. Это главный пункт резюме: на собеседовании вы будете рассказывать именно о нём.

> 💡 Не копируйте `exercises/` целиком. Создайте **новый** проект с нуля и перенесите только то, что понимаете и можете объяснить. Каждая строка должна быть вашей.

## Шаг 0. Новый репозиторий

```bash
mkdir qa-burger-tests          # каталог нового проекта (вне каталога курса)
cd qa-burger-tests             # переходим в него
git init                       # создаём git-репозиторий
```

- Каталог создаём **вне** курса, чтобы проект был самостоятельным и его можно было выложить отдельно.
- Скопируйте из курса `mvnw`, `mvnw.cmd` и `.mvn/` — тогда проекту не нужен установленный Maven (урок 6.1).
- Создайте `pom.xml` с зависимостями из `exercises/pom.xml` — только нужными вам.
- `.gitignore` с `target/`, `.idea/`, `allure-results/` — служебное в git не нужно.

## Обязательная часть (чек-лист приёмки)

### Структура и код
- [ ] Maven или Gradle проект, сборка одной командой `./mvnw test`
- [ ] Слои: тесты → шаги → клиенты API / Page Object → конфигурация и данные (урок 14.1)
- [ ] Конфигурация через Owner: `baseUrl`, учётные данные из переменных окружения, переключение окружения параметром `-Denv=` (урок 14.3)
- [ ] Модели запросов/ответов (record или Lombok), Jackson
- [ ] Генерация данных Datafaker, тесты не зависят друг от друга

### API (REST Assured), не меньше 15 тестов
- [ ] Регистрация и логин: позитивные и негативные (параметризованные)
- [ ] Каталог: фильтры, сортировка, пагинация
- [ ] Корзина и заказ: полный сценарий покупки
- [ ] Права доступа: пользователь не видит чужой заказ, не может создать товар (403)
- [ ] Проверка контракта через JSON Schema минимум для двух ответов
- [ ] Спецификации запросов/ответов, логирование в Allure

### UI (Selenide), не меньше 5 тестов
- [ ] Page Object для каталога, корзины, логина
- [ ] Локаторы через `data-testid`, проходят и на `?design=v2`
- [ ] Авторизация через API с подстановкой cookie (урок 10.14)
- [ ] Скриншот и page source в Allure при падении

### Интеграции
- [ ] Проверка заказа в БД через JDBC (профиль docker или H2 TCP — урок 11.7)
- [ ] Ожидание статуса заказа через Awaitility, без `Thread.sleep`
- [ ] Хотя бы один тест с WireMock вместо платёжного сервиса (успех + отказ)

### Отчёт и запуск
- [ ] Allure: `@Step`, `@Feature/@Story`, `@Severity`, ссылки, вложения
- [ ] Теги `smoke` / `regression` / `api` / `ui` и запуск по тегам
- [ ] Параллельный запуск API-тестов
- [ ] CI (GitHub Actions): запуск на push, Allure-отчёт как артефакт или GitHub Pages
- [ ] README: что тестируется, стек, как запустить локально, скриншот отчёта

### Охота на баги
- [ ] Включите в QA Burger режим загадки на странице `/admin` и найдите своими тестами не меньше **5 багов**. В README — таблица «баг → какой тест его ловит».

## Дополнительно (плюс на собеседовании)

- [ ] Kafka: проверка события `OrderCreated` своим consumer'ом
- [ ] Testcontainers: PostgreSQL и QA Burger поднимаются из теста
- [ ] Docker Compose: тесты + браузеры (Selenoid) одной командой
- [ ] Jenkinsfile с параметрами (окружение, теги, браузер)
- [ ] GraphQL- или SOAP-тест
- [ ] Перезапуск упавших тестов с отметкой в отчёте
- [ ] Скриншотное сравнение или мобильная эмуляция

## Как защищать проект на собеседовании

Подготовьте рассказ на 2–3 минуты:
1. **Что** тестируется и **зачем** такая архитектура.
2. **Один интересный тест**: какой баг ловит и как вы это проверили (что он падает при дефекте).
3. **Одна сложность**: например, нестабильный UI-тест и как вы нашли причину.
4. **Что улучшили бы** дальше.

## Самопроверка перед публикацией

- [ ] `git clone` в новый каталог → `./mvnw test` проходит без ручных шагов (кроме запуска QA Burger)
- [ ] В репозитории нет паролей, токенов, `target/`, `.idea/`
- [ ] Значок CI зелёный
- [ ] Все тесты понятны без чтения кода — по `@DisplayName` и шагам Allure
