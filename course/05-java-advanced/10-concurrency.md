Зачем автоматизатору потоки? Три причины:
1. **Параллельный запуск тестов** (модуль 14): 1000 тестов в 8 потоков идут в 8 раз быстрее — но только если тесты не мешают друг другу.
2. **Асинхронные системы** (модуль 13): QA Burger «готовит» заказ в фоновом потоке — тест должен уметь ждать.
3. **Нестабильные (flaky) тесты** часто вызваны именно проблемами многопоточности.

## Поток

**Поток** (thread) — независимая линия выполнения внутри программы. Обычная программа выполняется в одном потоке `main`. Можно запустить ещё:

```java
Thread t = new Thread(() -> System.out.println("Я в другом потоке: " + Thread.currentThread().getName()));
t.start();     // запустить параллельно
t.join();      // подождать, пока поток закончит
```

- в конструктор передаётся `Runnable` (лямбда без параметров и результата);
- `start()` — запустить; **не** `run()` (тот просто выполнит код в текущем потоке);
- `join()` — ждать завершения.

Порядок работы параллельных потоков **не определён**: каждый запуск может давать разный результат.

## ExecutorService — пул потоков

Создавать потоки вручную неудобно. Обычно используют **пул** — набор потоков, которым раздают задачи:

```java
ExecutorService pool = Executors.newFixedThreadPool(4);   // 4 потока
Future<String> future = pool.submit(() -> {               // отправить задачу (Callable)
    Thread.sleep(500);
    return "готово";
});
String result = future.get();     // ждать результат
pool.shutdown();                  // больше задач не будет — закрыть пул
```

- `submit(Callable)` — отправить задачу, вернуть **`Future`** — «обещание результата»;
- `future.get()` — дождаться и получить результат (если задача бросила исключение, `get` бросит `ExecutionException` с причиной внутри);
- `invokeAll(список задач)` — отправить все и дождаться всех; вернёт список `Future` **в том же порядке**;
- `shutdown()` — **обязательно** закрыть пул, иначе программа может не завершиться (потоки пула продолжают ждать задачи).

## Гонка (race condition)

```java
class ViewCounter {
    private int views = 0;
    void increment() { views++; }
}
```

8 потоков по 10 000 раз вызывают `increment()`. Ожидаем 80 000, получаем, например, 61 437 — и каждый раз разное число. Почему?

`views++` — это **три** действия: прочитать `views`, прибавить 1, записать. Два потока одновременно прочитали 100, оба прибавили 1, оба записали 101. Одно увеличение **потерялось**. Это и есть **состояние гонки**.

Решения:
- **`AtomicInteger`** — специальный класс, операции которого атомарны (неделимы):

  ```java
  private final AtomicInteger views = new AtomicInteger();
  void increment() { views.incrementAndGet(); }
  int get() { return views.get(); }
  ```

- **`synchronized`** — только один поток одновременно может выполнять метод:

  ```java
  synchronized void increment() { views++; }
  ```

- **Потокобезопасные коллекции**: `ConcurrentHashMap` вместо `HashMap`, `CopyOnWriteArrayList`.
- **Не делить состояние вообще** — лучший вариант. У каждого потока свои данные.

## Почему это важно для тестов

Тот самый `static` из урока 4.3:

```java
public class TestContext {
    public static String token;        // ❌ общий для всех тестов
}
```

Последовательно всё работает. Включили параллельный запуск — тест A записал токен пользователя anna, тест B перезаписал его токеном admin, тест A проверяет корзину anna с токеном admin и падает. Причём не всегда, а иногда — классический **flaky** тест.

Правила для параллельных тестов:
- никаких изменяемых `static` полей;
- каждый тест создаёт **свои** данные (свой пользователь с уникальным именем);
- общие ресурсы — потокобезопасные, или через `ThreadLocal` (у каждого потока своя копия; так Selenide хранит браузер для каждого потока).

## Thread.sleep — враг стабильных тестов

```java
pay(orderId);
Thread.sleep(5000);                 // ❌ «подождём, пока кухня приготовит»
assertThat(status(orderId)).isEqualTo("READY");
```

Проблемы:
- если кухня управилась за 1 секунду — 4 секунды потеряны впустую (на 500 тестах — полчаса);
- если сервер медленный и ему нужно 6 секунд — тест упал без бага.

Правильно — **ждать условие** с таймаутом: опрашивать статус каждые 200 мс, пока не станет READY или не выйдут 15 секунд. Это делает библиотека Awaitility (модуль 13), а Selenide делает так при каждой проверке автоматически (модуль 10).
