## Что такое UI-тест

**UI-автотест** управляет настоящим браузером так, как это делал бы человек: открывает страницы, вводит текст, нажимает кнопки, читает то, что на экране. Он проверяет систему **целиком** — от вёрстки и JavaScript до сервера и базы.

## Когда UI-тесты нужны, а когда нет

Вспомните пирамиду (урок 1.3): UI-тесты — **верхушка**. Они:
- **медленные**: открыть браузер, загрузить страницу, отрисовать — секунды на каждое действие;
- **хрупкие**: поменяли вёрстку — тест упал, хотя функциональность не сломана;
- **дорогие** в поддержке.

Поэтому UI-тестами проверяют то, что **нельзя** проверить ниже:
- ключевые сценарии пользователя от начала до конца (end-to-end): вход → корзина → заказ → оплата;
- логику на стороне браузера (JavaScript): счётчики, валидацию форм, динамическое появление элементов;
- интеграцию фронтенда с бэкендом: показывается ли то, что вернул сервер.

А расчёт скидки, валидацию данных, права доступа — проверяют **API-тестами** (модуль 9): в десятки раз быстрее и стабильнее.

> 💡 Отличный приём — **гибридные тесты**: подготовить данные через API (зарегистрировать пользователя, положить товары в корзину), а через UI проверить только то, что видит человек. Урок 10.14.

## Инструменты

| Инструмент | Язык | Особенности |
|---|---|---|
| **Selenium WebDriver** | Java, Python, C#, JS... | Стандарт индустрии (W3C WebDriver). Низкоуровневый: всё делаете сами, включая ожидания |
| **Selenide** | Java | Обёртка над Selenium: умные ожидания, лаконичный синтаксис, скриншоты при падении. Популярна в России |
| **Playwright** | Java, JS, Python, C# | Современный конкурент от Microsoft: быстрый, свои браузеры, автоожидания |
| **Cypress** | JavaScript | Популярен у фронтендеров, работает внутри браузера |
| **Appium** | разные | Мобильные приложения (тот же протокол WebDriver) |

В курсе: сначала **Selenium** (чтобы понимать основу и проходить собеседования — его спрашивают всегда), потом **Selenide** (на нём пишут в большинстве Java-проектов автотестов).

## Как работает Selenium

```text
  Ваш тест (Java)            драйвер браузера           браузер
 ┌──────────────┐  HTTP   ┌──────────────────┐       ┌──────────┐
 │ driver.get() │ ──────▶ │  chromedriver     │ ────▶ │  Chrome  │
 │ .click()     │ ◀────── │ (W3C WebDriver)  │ ◀──── │          │
 └──────────────┘  JSON   └──────────────────┘       └──────────┘
```

- Тест вызывает методы Selenium (`driver.get(...)`, `element.click()`).
- Selenium превращает их в HTTP-запросы по протоколу **W3C WebDriver** к **драйверу** браузера (chromedriver, geckodriver для Firefox, msedgedriver).
- Драйвер управляет браузером и возвращает результат.

Драйвер должен подходить к версии браузера. Раньше его качали вручную (и ловили ошибку «This version of ChromeDriver only supports Chrome version 116»). С Selenium 4.6 **Selenium Manager** находит браузер и скачивает нужный драйвер сам — в курсе ничего ставить не нужно, кроме Chrome.

## Что входит в UI-тест

1. **Открыть браузер** с нужными настройками (размер окна, headless — без окна, язык).
2. **Открыть страницу**.
3. **Найти элементы** — для этого нужны **локаторы** (уроки 10.2–10.3).
4. **Действовать**: клик, ввод, выбор, наведение.
5. **Дождаться** нужного состояния (урок 10.5) — самое коварное место.
6. **Проверить** результат.
7. **Закрыть браузер** — всегда, даже при падении теста.

## Где здесь QA Burger

Для UI-тестов у нас есть:
- **магазин** (http://localhost:8081): каталог, товар, корзина, заказы, вход — с атрибутами `data-testid` у важных элементов;
- **дизайн v2** (`?design=v2`): та же функциональность с другой вёрсткой — проверка устойчивости локаторов;
- **Песочница** (http://localhost:8081/playground): формы, алерты, iframe, drag&drop, файлы, динамические элементы — всё, что встречается в реальных сайтах;
- баги интерфейса BUG-601, 701, 702, 703 для Test Lab.

Задания модуля открывают браузер из IDEA против запущенного QA Burger. Проверки («▶ Проверить») запускают браузер **без окна** (headless) и свой экземпляр приложения — окно не появится, это нормально.
