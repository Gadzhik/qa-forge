Разберём несколько готовых шаблонов промптов для ежедневных задач. Скопируйте их себе и адаптируйте.

## 1. Анализ требований

```text
Ниже требования к функции. Найди: противоречия, неоднозначности, непроверяемые формулировки,
пропущенные сценарии (ошибки, пустые значения, права доступа, повторные действия, параллельность).
Ответ: список «проблема — почему это проблема — вопрос к аналитику». Ничего не придумывай.

<текст требований>
```

Модель хорошо находит «а что если» (урок 1.4) — используйте её как второго рецензента.

## 2. Тест-дизайн по технике

```text
Поле «количество» принимает целые от 1 до 99. Применить классы эквивалентности и анализ граничных значений.
Выведи таблицу: класс | значение | ожидание. Отдельно — значения неверного типа.
```

Указывайте **технику** — ответ будет системным, а не случайным набором.

## 3. Модель и схема по JSON

```text
Вот пример ответа API. Сгенерируй:
1) Java 21 record с Jackson-аннотациями (snake_case → camelCase, деньги — BigDecimal, неизвестные поля игнорировать);
2) JSON Schema draft-04 со строгими типами, required и additionalProperties: false.

<JSON>
```

Затем — проверка в тренажёре [**POJO Builder**](#/game/pojo-builder) или тестом (урок 9.7).

```text
Вот HTML формы входа. Напиши Page Object на Selenide (Java 21): локаторы только по data-testid,
```

## 5. Разбор упавшего теста

```text
Автотест на Java (REST Assured + JUnit 5) упал. Ниже код теста, сообщение об ошибке, запрос/ответ и логи сервиса за это время.
Определи вероятную причину: баг продукта, ошибка теста, проблема окружения. Приведи аргументы из данных.
Если данных не хватает — скажи, что ещё посмотреть.

<код теста> <ошибка> <вложения> <логи, обезличенные>
```

Слова «приведи аргументы из данных» заставляют модель опираться на ваши факты, а не на общие рассуждения.

## 6. Ревью тестов

```text
Сделай ревью этого автотеста по критериям: независимость, детерминированность, конкретность проверок,
ожидания вместо sleep, читаемость, ловит ли он дефект (каким изменением кода приложения тест можно «обмануть»?).
```

Последний вопрос — «какой мутант выживет» (урок 7.1) — особенно полезен.

## 7. Генерация «злых» данных

```text
Сгенерируй 20 значений для поля «имя пользователя» (ограничение 3–30 символов, латиница/цифры/_),
которые проверяют: границы длины, недопустимые символы, Unicode, пробелы, SQL- и XSS-инъекции, пустоту.
Формат: CSV value,expected(valid|invalid),reason
```

Результат — прямо в `@CsvFileSource` (урок 7.4).

## Правила проверки результата

1. **Код**: компилируется → проходит на исправном приложении → падает с внесённым дефектом.
2. **Требования**: каждое утверждение модели сверено с документом.
3. **Библиотеки и методы**: существуют в вашей версии (откройте документацию или автодополнение IDE).
4. **Факты о продукте**: только из ваших данных — модель не знает ваш продукт.

## Где ИИ не заменит тестировщика

- понимание **бизнеса** и пользователей: что на самом деле важно;
- **исследовательское** тестирование: заметить странное, чего нет в требованиях;
- решение, **достаточно ли** протестировано и можно ли выпускать;
- ответственность за качество.

ИИ — сильный инструмент, который делает хорошего тестировщика быстрее. Плохого — только увереннее в ошибках.
