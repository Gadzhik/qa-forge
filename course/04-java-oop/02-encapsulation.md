## Проблема

Представим, что поле количества открыто:

```java
public class CartItem {
    public int quantity;
}

CartItem item = new CartItem();
item.quantity = -5;      // никто не помешал
```

Любой код в программе может записать в `quantity` что угодно: −5, 0, миллион. Правило «от 1 до 99» придётся проверять в каждом месте, где меняют количество, — и где-нибудь обязательно забудут. Именно так рождаются баги вроде BUG-301.

## Решение — инкапсуляция

**Инкапсуляция** — один из трёх китов ООП (вместе с наследованием и полиморфизмом). Идея: **спрятать данные внутри объекта**, а изменять их только через методы, которые соблюдают правила.

```java
public class CartItem {
    private int quantity = 1;

    public int getQuantity() {
        return quantity;
    }

    public boolean changeQuantity(int newQuantity) {
        if (newQuantity < 1 || newQuantity > 99) {
            return false;            // некорректное значение — отказываем
        }
        quantity = newQuantity;
        return true;
    }
}
```

Теперь испортить количество снаружи невозможно: поле `private`, а единственный способ его изменить — `changeQuantity`, которая проверяет диапазон. Правило записано **в одном месте**.

> 💡 Метод, меняющий поле, называют **сеттером** (set — установить): `setQuantity(int q)`. Но не у всех полей должен быть сеттер! Если значение не должно меняться после создания (как имя товара в позиции корзины), сделайте поле `final` и не пишите сеттер.

## Модификаторы доступа

| Модификатор | Кому доступно |
|---|---|
| `private` | только внутри этого класса |
| *(без модификатора)* — «package-private» | классам из того же пакета |
| `protected` | тому же пакету + наследникам (урок 4.5) |
| `public` | всем |

Правило по умолчанию: **поля — `private`**, методы — `public` только те, которые нужны снаружи, остальные — `private`.

> 💡 Тест-классы JUnit 5 и их методы можно не делать `public` — так и пишут: `class CartTest { @Test void addsItem() {...} }`. JUnit находит их сам. Именно поэтому проверки в курсе объявлены без `public`.

## final для полей

```java
private final String productName;
```

`final` поле:
- должно получить значение в конструкторе (или сразу при объявлении);
- больше никогда не меняется.

Это делает объект надёжнее: меньше состояний, меньше багов. Хорошее правило: делайте поля `final`, если нет причин их менять.

## Пакеты и import

Модификаторы связаны с **пакетами**. Чтобы использовать класс из другого пакета, его нужно **импортировать**:

```java
package ru.qacourse.m04;

import java.util.List;                  // один класс
import java.util.*;                     // все классы пакета (так делать не рекомендуется)
import static org.assertj.core.api.Assertions.assertThat;  // статический метод
```

- Классы из пакета `java.lang` (`String`, `Math`, `Integer`, `System`) импортировать не нужно — они доступны всегда.
- `import static` позволяет вызывать статический метод без имени класса: `assertThat(x)` вместо `Assertions.assertThat(x)`. Мы будем так делать во всех тестах.

IDEA добавляет импорты сама (Alt+Enter на красном имени класса).

## Связь с тестированием

Инкапсуляция — причина, по которой автотесты проверяют **поведение через публичный интерфейс**, а не лезут во внутренности. Тест `CartItemCheck` из задания не знает, как вы храните количество, — он вызывает `changeQuantity` и смотрит `getQuantity`. Так же API-тест не знает про базу данных QA Burger — он отправляет запросы и смотрит ответы.

```task
id: m04-t02
title: Позиция корзины с проверкой количества
module: exercises/m04-java-oop
test: CartItemCheck
file: exercises/m04-java-oop/src/main/java/ru/qacourse/m04/CartItem.java
solution: solutions/exercises/m04-java-oop/src/main/java/ru/qacourse/m04/CartItem.java
text: |
  - `changeQuantity(newQuantity)` — меняет количество, только если оно от 1 до 99; возвращает `true`/`false`;
  - `increment()` — +1, но не больше 99 (переиспользуйте `changeQuantity`!).
hint: |
  В `increment` достаточно одной строки: `changeQuantity(quantity + 1);` — проверка границы уже есть в `changeQuantity`.
```
