## Что такое фреймворк автотестов

Когда тестов десяток — можно писать «как получится». Когда их тысяча и над ними работают пять человек — нужен **фреймворк**: договорённости о структуре и общий код, на котором тесты пишутся быстро и одинаково.

Признаки хорошего фреймворка:
- **новый тест — несколько строк**, только суть проверки;
- **изменение приложения правится в одном месте** (адрес ручки, локатор, формат ответа);
- тесты **независимы** и могут идти **параллельно**;
- запускаются **одной командой** на любом стенде;
- **отчёт** понятен не только автору: что упало, на каком шаге, с какими данными.

## Слои

```text
┌───────────────────────────────────────────────────────────────┐
│  tests        — тесты: сценарии и проверки (что проверяем)     │
├───────────────────────────────────────────────────────────────┤
│  steps / api clients / pages — действия (как делаем)           │
├───────────────────────────────────────────────────────────────┤
│  models (DTO)  │  data (тестовые данные)  │  assertions         │
├───────────────────────────────────────────────────────────────┤
│  config (адреса, логины, таймауты) │ extensions (JUnit)        │
├───────────────────────────────────────────────────────────────┤
│  библиотеки: JUnit, REST Assured, Selenide, AssertJ, Allure    │
└───────────────────────────────────────────────────────────────┘
```

Каждый слой знает только о слоях **ниже**. Тест не знает URL ручки и локаторы — он вызывает `orders.create("SALE10")`. Клиент не знает о проверках — он отправляет запрос и возвращает модель.

### Почему клиенты — в `src/main`

Код фреймворка (клиенты, модели, конфиг) — это **библиотека**, которую используют тесты. Положив её в `main`, можно в будущем вынести фреймворк в отдельный модуль/артефакт и подключать в разные проекты тестов. Многие команды держат всё в `src/test` — тоже нормально; главное — одинаково.

## Клиент API

```java
public class CartClient {
    private final RequestSpecification spec;

    public CartClient(String token) {
        this.spec = Specs.withToken(token);
    }

    @Step("Добавить в корзину товар {productId} × {quantity}")
    public CartClient add(long productId, int quantity) {
        given(spec).body(Map.of("productId", productId, "quantity", quantity))
                .post("/api/cart/items").then().statusCode(200);
        return this;
    }

    @Step("Получить корзину")
    public CartDto get() {
        return given(spec).get("/api/cart").then().statusCode(200).extract().as(CartDto.class);
    }
}
```

- один метод — одна ручка API;
- **ожидаемый статус проверяется в клиенте** (позитивный путь); для негативных сценариев — отдельный метод `try...()`, возвращающий «сырой» ответ (см. `OrderClient.tryCreate`);
- возвращает **модель**, а не `Response` — тест работает с типизированными данными;
- `return this` — цепочки `cart.clear().add(...).add(...)`;
- `@Step` — шаг в отчёте Allure (урок 14.2).

## Тест на фреймворке

```java
@Test
@DisplayName("Заказ из корзины: сумма = цена × количество, статус NEW")
void orderFromCart() {
    cart.add(CLASSIC_BURGER, 2);
    OrderDto order = orders.create(null);
    assertThat(order.status()).isEqualTo("NEW");
    assertThat(order.total()).isEqualByComparingTo("579.80");
    assertThat(cart.get().items()).isEmpty();
}
```

Ни одного URL, JSON или токена — только сценарий. Сравните с тестами модуля 9.

## Другие паттерны

- **Steps** (шаги) — слой бизнес-действий поверх клиентов и страниц: `checkoutSteps.buyAsNewUser(BURGER)`. Удобен, когда сценарии включают и API, и UI.
- **Builder / Factory тестовых данных** — `TestUsers.random()`, `OrderBuilder.withPromo("SALE10").build()`.
- **Assertions-слой** — свои проверки предметной области: `assertThatOrder(order).isPaid().hasTotal("521.82")` (custom AssertJ assertions).
- **Page Object / компоненты** для UI (урок 10.9).

## Типичные ошибки архитектуры

- «Божественный» `BaseTest` на 2000 строк, от которого наследуется всё.
- Проверки внутри клиентов и страниц (тогда негативные тесты писать невозможно).
- Статические изменяемые поля с токенами и данными → поломка при параллельности (урок 14.4).
- Копипаста вместо переиспользования (и наоборот — переусложнение ради 3 тестов).
- Зашитые адреса и пароли вместо конфигурации.
