## Два разных слова

- **Аутентификация** — проверка, **кто вы**: логин и пароль, отпечаток пальца, токен. Не прошли — **401**.
- **Авторизация** — проверка, **что вам можно**: обычный пользователь не может удалять товары, чужой заказ смотреть нельзя. Нельзя — **403** (или 404, чтобы не раскрывать существование ресурса — так QA Burger делает с чужими заказами).

Для тестировщика это огромная область проверок: доступ без входа, с чужим токеном, с просроченным токеном, с правами пользователя к ручкам администратора.

## HTTP Basic Auth

Самый простой способ: в каждом запросе заголовок

```http
Authorization: Basic YWRtaW46YWRtaW4=
```

`YWRtaW46YWRtaW4=` — это `admin:admin`, закодированное в **Base64**. Base64 — **не шифрование**, а просто способ записать данные безопасными символами; раскодировать может кто угодно. Поэтому Basic Auth используют только поверх HTTPS.

Попробуйте: http://localhost:8081/playground/basic-auth — браузер покажет окно логина (это реакция на ответ `401` с заголовком `WWW-Authenticate: Basic`). Логин `admin`, пароль `admin`. Из curl: `curl -u admin:admin http://localhost:8081/playground/basic-auth`.

Кодирование в Java:

```java
String header = "Basic " + Base64.getEncoder().encodeToString("admin:admin".getBytes(StandardCharsets.UTF_8));
```

## Сессии и cookies

Классический способ для сайтов:

1. Пользователь отправляет форму логина.
2. Сервер проверяет пароль и отвечает заголовком `Set-Cookie: SESSION=abc123` — создаёт **сессию** и выдаёт её идентификатор.
3. Браузер **сам** сохраняет cookie и отправляет её с каждым следующим запросом к этому сайту: `Cookie: SESSION=abc123`.
4. Сервер по идентификатору находит сессию и понимает, кто это.

**Cookie** — пара имя=значение, которую сайт хранит в браузере. У неё есть атрибуты: `Path`, `Domain`, `Expires`/`Max-Age` (срок жизни), `HttpOnly` (недоступна из JavaScript — защита от кражи через XSS), `Secure` (только по HTTPS), `SameSite`.

## JWT — токены

Современные API чаще используют **токены**. QA Burger — **JWT** (JSON Web Token, читается «джот»).

Получение: `POST /api/auth/login` → `{"token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIyIiwidXNlcm5hbWUiOiJ1c2VyIiwicm9sZSI6IlVTRVIiLCJpYXQiOjE3MTU1MTUyNzUsImV4cCI6MTcxNTU0NDA3NX0.xxx"}`.

Использование — заголовок в каждом запросе:

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9....
```

**Bearer** — «предъявитель»: кто предъявил токен, тот и пользователь. Поэтому токен — секрет, как пароль.

### Устройство JWT

Три части через точку: `ЗАГОЛОВОК.ДАННЫЕ.ПОДПИСЬ`, каждая в Base64URL.

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9   →  {"alg":"HS256","typ":"JWT"}
.
eyJzdWIiOiIyIiwidXNlcm5hbWUiOiJ1c2VyIi...  →  {"sub":"2","username":"user","role":"USER","iat":1715515275,"exp":1715544075}
.
xxx  →  подпись
```

- **Заголовок** — алгоритм подписи;
- **Данные (payload, claims)** — кто пользователь: `sub` — id, `role` — роль, `iat` — когда выдан, `exp` — когда истекает (секунды с 1970 года);
- **Подпись** — сервер вычисляет её секретным ключом. Если кто-то изменит данные (например, `role` на `ADMIN`), подпись перестанет сходиться, и сервер токен отвергнет.

Данные JWT **не зашифрованы** — их видит любой. Вставьте свой токен на https://jwt.io — увидите содержимое. Поэтому в JWT не кладут секретов.

**Что проверять в API с JWT:**
- запрос без токена → 401;
- с мусором вместо токена → 401;
- с **испорченной подписью** (изменили один символ в последней части) → 401;
- с **просроченным** токеном → 401;
- с токеном пользователя к ручке администратора → 403;
- с токеном пользователя A к данным пользователя B → 403/404 (BUG-204);
- токен после выхода (logout) — зависит от требований.

### Токен в cookie

QA Burger кладёт тот же JWT ещё и в cookie `token` при входе через форму — так страницы сайта узнают пользователя. Сервер принимает токен из обоих мест. В модуле 10 мы этим воспользуемся: получим токен через API и **положим cookie в браузер**, чтобы UI-тест начинался уже «залогиненным», без медленного заполнения формы.

## OAuth 2.0 и OpenID Connect — для общего развития

Кнопка «Войти через Google/Яндекс/VK» — это **OAuth 2.0** + **OpenID Connect**. Схема сложнее: приложение перенаправляет пользователя на сервер авторизации, тот после входа выдаёт **access token** (часто — JWT) и **refresh token** (чтобы получить новый access, когда старый истечёт). В автотестах обычно получают токен напрямую у сервера авторизации специальным запросом (`grant_type=password` или `client_credentials` для тестовых клиентов) — детали уточняйте у разработчиков своего проекта.

## API-ключи

Ещё вариант — постоянный ключ в заголовке: `X-API-Key: 7f3a...`. Часто у сервисов для интеграций (платёжные системы, карты).

> ⚠️ Токены, ключи, пароли — **никогда** не коммитить в репозиторий и не печатать в открытом виде в отчётах. В CI — секретные переменные (урок 6.7).
