REST — самый распространённый стиль API, но не единственный. В вакансиях встречаются и другие. Разберём каждый, а GraphQL и SOAP попробуем руками на QA Burger.

## GraphQL

**GraphQL** (разработан в Facebook) — язык запросов, в котором **клиент сам решает, какие поля получить**. Один адрес (`POST /graphql`), а в теле — запрос.

Проблема REST, которую он решает: экрану нужен товар с названием, ценой и оценками отзывов. В REST — два запроса (`/products/1` и `/products/1/reviews`), и оба вернут много лишних полей. В GraphQL — один запрос и ровно нужные поля:

```graphql
{
  product(id: 1) {
    name
    price
    reviews {
      rating
    }
  }
}
```

Ответ повторяет форму запроса:

```json
{
  "data": {
    "product": {
      "name": "Классический бургер",
      "price": 289.9,
      "reviews": [ { "rating": 5 }, { "rating": 4 } ]
    }
  }
}
```

**Попробуйте:** откройте http://localhost:8081/graphiql — интерактивная консоль. Слева пишете запрос (Ctrl+Space — подсказки полей), справа ответ. Кнопка **Docs** — схема: какие запросы и поля есть. Схема QA Burger — в файле `shop-app/src/main/resources/graphql/schema.graphqls`.

Запросы с параметрами:

```graphql
{ products(category: DRINK) { id name price } }
```

Через curl GraphQL — это обычный POST с JSON, где запрос лежит строкой в поле `query`:

```bash
curl -X POST http://localhost:8081/graphql -H "Content-Type: application/json" \
     -d '{"query": "{ product(id: 1) { name price } }"}'
```

Основные понятия: **query** (чтение), **mutation** (изменение), **subscription** (подписка на события), **схема** (типы и поля — контракт).

**Особенности тестирования GraphQL:**
- код ответа почти всегда **200**, даже при ошибке! Ошибки приходят в поле `errors` тела. Тест обязан проверять `errors`, а не только статус;
- проверка схемы (запрос несуществующего поля → ошибка валидации);
- глубокие вложенные запросы (могут «положить» сервер — проверка на ограничения);
- одинаковость данных с REST (BUG-901 — цена в GraphQL без копеек).

## SOAP

**SOAP** — старший брат REST: протокол на **XML** со строгим контрактом. Встречается в банках, страховании, госсистемах, интеграциях с 1С.

- Контракт описывается файлом **WSDL** (Web Services Description Language) — какие операции и какие XML-структуры. WSDL QA Burger: http://localhost:8081/ws/delivery.wsdl
- Запрос и ответ — XML-«конверт» (`Envelope`) с телом (`Body`):

```xml
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/"
               xmlns:d="http://qaburger.local/delivery">
  <soap:Body>
    <d:CalculateDeliveryRequest>
      <d:distanceKm>4</d:distanceKm>
      <d:orderAmount>500</d:orderAmount>
    </d:CalculateDeliveryRequest>
  </soap:Body>
</soap:Envelope>
```

- `xmlns:...` — **пространства имён** XML: префиксы `soap:` и `d:` указывают, из какого «словаря» каждый тег. В тестах о них часто спотыкаются;
- ответ — тоже конверт: `<d:cost>199.00</d:cost>`;
- ошибка — элемент `<soap:Fault>` (и обычно HTTP 500).

**Попробуйте** (сохраните XML выше в файл `delivery.xml`):

```bash
curl -X POST http://localhost:8081/ws/delivery -H "Content-Type: text/xml" -d @delivery.xml
```

Популярный инструмент для ручной работы с SOAP — **SoapUI**: загружаете WSDL, он сам генерирует шаблоны запросов. В автотестах SOAP отправляют REST Assured'ом (это всё равно HTTP POST) и разбирают ответ через XmlPath.

Правило QA Burger: доставка 99 ₽ + 25 ₽/км, бесплатно от 1000 ₽. Подумайте о граничных значениях: 0 км (BUG-902), 999 и 1000 ₽, отрицательное расстояние.

## gRPC

**gRPC** (от Google) — быстрый протокол для общения **сервисов между собой**. Вместо JSON — двоичный формат **Protocol Buffers**, контракт описывается в файлах `.proto`:

```protobuf
service OrderService {
  rpc GetOrder (OrderRequest) returns (OrderReply);
}
message OrderRequest { int64 id = 1; }
message OrderReply { int64 id = 1; string status = 2; double total = 3; }
```

Из `.proto` генерируется Java-код клиента — тест вызывает удалённый метод как обычный: `stub.getOrder(request)`. Работает поверх HTTP/2, поддерживает потоки данных. Ручные инструменты: **grpcurl**, Postman (умеет gRPC), BloomRPC/Kreya. Статусы свои: `OK`, `NOT_FOUND`, `INVALID_ARGUMENT`, `UNAUTHENTICATED`, `PERMISSION_DENIED`...

## WebSocket

Обычный HTTP: клиент спросил — сервер ответил, соединение закрыто. **WebSocket** — постоянное **двустороннее** соединение: сервер может сам присылать сообщения, когда что-то произошло. Используется в чатах, биржевых котировках, онлайн-играх, уведомлениях («ваш заказ готов!»).

- адрес: `ws://` или `wss://` (зашифрованный);
- соединение начинается как HTTP-запрос с заголовком `Upgrade: websocket` (ответ `101 Switching Protocols`);
- в DevTools — вкладка Network → фильтр **WS** → вкладка **Messages**.

Тестирование: подключиться, отправить сообщение, **дождаться** ответа (асинхронно, с таймаутом — модуль 13), проверить переподключение при обрыве.

## Вебхуки (webhooks)

**Вебхук** — «обратный вызов»: не вы спрашиваете сервис, а он сам отправляет HTTP-запрос на ваш адрес, когда происходит событие. Пример: платёжная система после оплаты делает `POST https://qaburger.ru/payments/callback {"orderId": 42, "status": "APPROVED"}`.

Тестирование вебхуков: нужно поднять **свой сервер-приёмник** в тесте (WireMock, модуль 12) и проверить, что сервис отправил на него правильный запрос; или наоборот — отправить в тестируемую систему «поддельный» вебхук и проверить реакцию.

## Брокеры сообщений (Kafka, RabbitMQ)

Сервисы общаются ещё и **асинхронными сообщениями** через брокер: сервис заказов кладёт событие «заказ оплачен» в топик, кухня его читает. Это не HTTP, но тоже контракт (формат сообщения). Подробно — модуль 13; в QA Burger события можно посмотреть уже сейчас: http://localhost:8081/api/debug/events

## Сравнение

| | REST | GraphQL | SOAP | gRPC | WebSocket |
|---|---|---|---|---|---|
| Формат | JSON | JSON | XML | Protobuf (двоичный) | любой (часто JSON) |
| Контракт | OpenAPI | Схема GraphQL | WSDL | .proto | нет стандарта |
| Где | Везде | Фронтенд ↔ бэкенд | Банки, интеграции | Сервис ↔ сервис | Real-time |
| Ошибки | HTTP-коды | Поле `errors`, код 200 | `<Fault>` | Статусы gRPC | Сообщения |
