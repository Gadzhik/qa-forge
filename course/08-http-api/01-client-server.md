## Клиент и сервер

Почти всё в современном IT устроено по схеме **клиент — сервер**:

- **Сервер** — программа, которая **ждёт запросов** и отвечает на них. QA Burger — сервер: он запущен и слушает порт 8081.
- **Клиент** — программа, которая **отправляет запросы**: браузер, мобильное приложение, другой сервис... и **ваш автотест**.

```text
   Клиент                                   Сервер (QA Burger)
 ┌──────────┐   запрос: «дай товар №1»     ┌──────────────────┐
 │ браузер  │ ───────────────────────────▶ │  принимает,      │
 │ автотест │                              │  ищет в базе,    │
 │ curl     │ ◀─────────────────────────── │  формирует ответ │
 └──────────┘   ответ: {"name": "..."}     └──────────────────┘
```

Когда вы нажимаете «В корзину» на сайте, браузер отправляет серверу запрос. Автотест может отправить **тот же самый запрос напрямую**, без браузера, — это и есть **API-тестирование**. Оно быстрее и стабильнее UI-тестов (вспомните пирамиду, урок 1.3).

## API

**API** (Application Programming Interface) — «интерфейс для программ»: набор правил, по которым одна программа может обращаться к другой. Пользовательский интерфейс (UI) — для людей: кнопки и формы. API — для программ: адреса и данные в формате JSON.

У QA Burger есть и UI (страницы магазина), и API (`/api/...`). Причём UI сам пользуется API: страница товара отправляет `POST /api/cart/items` (вы видели это во вкладке Network, урок 2.5).

## Микросервисы

В крупных компаниях система — это десятки или сотни **сервисов**, общающихся друг с другом через API: сервис заказов, сервис оплаты, сервис уведомлений, склад... QA Burger тоже «звонит» внешнему платёжному сервису при оплате (`shop.payment.url`). Тестировщик проверяет и каждый сервис отдельно, и их взаимодействие. Когда внешний сервис недоступен для тестов, его подменяют **заглушкой** (WireMock, модуль 12).

## URL — адрес ресурса

```text
http://localhost:8081/api/products?category=DRINK&page=0#top
└┬─┘   └───┬───┘└┬─┘└─────┬─────┘└──────────┬──────────┘└┬┘
схема    хост  порт     путь              запрос     фрагмент
```

| Часть | Пример | Что значит |
|---|---|---|
| **Схема (протокол)** | `http`, `https` | Как общаемся. `https` — с шифрованием |
| **Хост** | `localhost`, `api.qaburger.ru`, `192.168.1.10` | Какой компьютер |
| **Порт** | `8081` | Какая программа на этом компьютере |
| **Путь** | `/api/products` | Какой ресурс на сервере |
| **Строка запроса (query)** | `?category=DRINK&page=0` | Параметры: после `?`, пары `ключ=значение` через `&` |
| **Фрагмент** | `#top` | Место на странице; на сервер не отправляется |

### Хост, IP и DNS

У каждого компьютера в сети есть **IP-адрес** (например, `93.184.216.34`). Людям удобнее имена — `api.qaburger.ru`. **DNS** — «телефонная книга» интернета, которая превращает имя в IP.

**`localhost`** — особое имя, означающее «этот же компьютер» (IP `127.0.0.1`). Поэтому `http://localhost:8081` — «программа на моём компьютере, на порту 8081».

### Порт

На одном компьютере работает много серверных программ. **Порт** — номер «двери», которую слушает конкретная программа: портал — 8080, QA Burger — 8081, PostgreSQL — 5432, Kafka — 9092.

Если порт в URL не указан, используется стандартный: **80** для `http`, **443** для `https`. Поэтому в `https://google.com` порта не видно.

> ⚠️ Ошибка `Connection refused` означает: по этому адресу и порту никто не слушает — сервер не запущен или вы ошиблись портом. Самая частая причина «упали все API-тесты разом».

### Кодирование URL

В URL нельзя просто так писать пробелы и русские буквы. Их **кодируют** (percent-encoding): пробел → `%20` (или `+` в параметрах), `бургер` → `%D0%B1%D1%83%D1%80%D0%B3%D0%B5%D1%80`. Браузер и библиотеки (REST Assured) делают это сами, а вот если склеиваете URL строками вручную — легко получить баг.

## HTTP и HTTPS

**HTTP** — протокол (набор правил), по которому клиент и сервер общаются в вебе. Следующий урок целиком о нём.

**HTTPS** — тот же HTTP, но поверх зашифрованного соединения (TLS). Посторонние не могут прочитать или подменить данные. Все публичные сайты сейчас на HTTPS. Учебный QA Burger работает на HTTP — для локального компьютера шифрование не нужно.

> 💡 Иногда на тестовых стендах HTTPS-сертификат «самоподписанный», и клиент ругается: `PKIX path building failed` / `unable to find valid certification path`. В REST Assured для тестовых стендов это обходят `relaxedHTTPSValidation()`. В проде так делать нельзя.

> 🧪 **Попробуй сам.** Откройте в браузере http://localhost:8081/api/products?category=DRINK&size=2 — браузер тоже клиент, и он покажет «сырой» JSON-ответ API. Поменяйте параметры в адресе.
