## Что такое REST

**REST** — архитектурный стиль построения API поверх HTTP. Не стандарт и не библиотека, а набор принципов. API, построенное по ним, называют **RESTful**. Главные идеи:

1. **Ресурсы** — всё, с чем работает API, — это ресурсы с адресами: товары `/api/products`, конкретный товар `/api/products/1`, его отзывы `/api/products/1/reviews`.
2. **Действие задаётся методом HTTP**, а не адресом: не `/api/getProduct?id=1` и `/api/deleteProduct?id=1`, а `GET /api/products/1` и `DELETE /api/products/1`.
3. **Без состояния (stateless)**: каждый запрос самодостаточен — сервер не помнит предыдущие запросы клиента. Поэтому токен передаётся **в каждом** запросе.
4. **Единый формат** представления — обычно JSON.

### Типичная схема адресов (CRUD)

**CRUD** — Create, Read, Update, Delete: четыре базовых операции.

| Операция | Метод и путь | Ответ |
|---|---|---|
| Список | `GET /api/products` | 200 + массив/страница |
| Один | `GET /api/products/{id}` | 200 / 404 |
| Создать | `POST /api/products` + тело | 201 + созданный объект |
| Заменить | `PUT /api/products/{id}` + тело | 200 |
| Удалить | `DELETE /api/products/{id}` | 204 |

`{id}` — **параметр пути** (path parameter): часть адреса, которая меняется.

### Параметры пути и запроса

- **Path-параметр** идентифицирует ресурс: `/api/orders/42` — заказ №42.
- **Query-параметры** уточняют выборку: фильтр, сортировка, пагинация — `/api/products?category=DRINK&sort=price,desc&page=0&size=5`.

## Пагинация

Товаров может быть миллион — отдавать все сразу нельзя. Ответ режут на **страницы**:

```json
{
  "content": [ { "id": 1, ... }, { "id": 2, ... } ],
  "page": 0,
  "size": 2,
  "totalElements": 20,
  "totalPages": 10
}
```

Что проверять: что сумма элементов по всем страницам = `totalElements` (BUG-101!), что последняя страница неполная, что страница за пределами — пустая, что `size=0` и `size=1000` обрабатываются корректно.

## Ошибки в QA Burger

Все ошибки API приходят в одном формате:

```json
{
  "timestamp": "2024-05-12T12:02:40Z",
  "status": 400,
  "code": "BAD_QUANTITY",
  "message": "Количество должно быть больше 0",
  "path": "/api/cart/items",
  "fields": null
}
```

Проверять в негативных тестах нужно не только статус, но и **машиночитаемый код** (`code`) — его используют клиенты, — и наличие понятного `message`.

## Карта API QA Burger

Полная документация — в Swagger: http://localhost:8081/swagger-ui.html. Краткая карта:

| Метод и путь | Авторизация | Что делает |
|---|---|---|
| `POST /api/auth/register` | — | Регистрация → 201 + пользователь |
| `POST /api/auth/login` | — | Вход → `{"token": "...", "type": "Bearer"}` |
| `GET /api/auth/me` | токен | Текущий пользователь |
| `GET /api/products` | — | Каталог: `search`, `category`, `sort`, `page`, `size` |
| `GET /api/products/{id}` | — | Товар |
| `POST/PUT/DELETE /api/products[/{id}]` | токен ADMIN | Управление товарами |
| `GET/POST /api/products/{id}/reviews` | POST — токен | Отзывы |
| `GET /api/cart` | токен | Корзина |
| `POST /api/cart/items` | токен | Добавить `{"productId", "quantity"}` |
| `DELETE /api/cart/items/{productId}` | токен | Убрать товар |
| `DELETE /api/cart` | токен | Очистить корзину |
| `POST /api/orders` | токен | Оформить заказ `{"promoCode": "SALE10"}` |
| `GET /api/orders`, `GET /api/orders/{id}` | токен | Мои заказы / заказ |
| `POST /api/orders/{id}/pay` | токен | Оплатить |
| `POST /api/orders/{id}/cancel` | токен | Отменить |
| `GET /api/orders/{id}/receipt.pdf` | токен | Чек PDF |
| `GET /api/orders/export.xlsx` | токен | Выгрузка Excel |
| `POST /api/files`, `GET /api/files/{id}` | — | Загрузка и скачивание файлов |
| `POST /graphql` | — | GraphQL (урок 8.6) |
| `POST /ws/delivery` | — | SOAP: стоимость доставки (урок 8.6) |
| `GET/PUT /api/admin/bugs`, `POST /api/admin/reset` | — | Служебное: баги тренажёра, сброс данных |
| `GET /api/debug/logs`, `GET /api/debug/events` | — | Логи и события (модули 13, 16) |

> 💡 Служебные ручки `/api/admin/reset` и `/api/debug/*` — пример того, что в реальных проектах QA часто просит у разработчиков: **тестовые ручки** для подготовки данных и диагностики, доступные только на тестовых стендах.

## Документация API: OpenAPI и Swagger

**OpenAPI** — стандарт описания REST API: какие есть адреса, параметры, форматы запросов и ответов, коды. Описание лежит в JSON/YAML (у QA Burger — http://localhost:8081/v3/api-docs).

**Swagger UI** — веб-страница, которая по этому описанию рисует интерактивную документацию с кнопкой «попробовать».

Для тестировщика OpenAPI-описание — это **контракт**: требования, по которым пишут API-тесты. Расхождение реального поведения с описанием — дефект (либо в коде, либо в документации). По OpenAPI можно даже генерировать модели для тестов и проверять схемы ответов (модуль 9).

```quiz
- q: Какой адрес соответствует стилю REST для получения заказа №5?
  options: ["GET /api/orders/5", "GET /api/getOrder?id=5", "POST /api/orders/get/5"]
  answer: 0
- q: Что означает stateless в REST?
  options:
    - "Сервер не хранит состояние между запросами: каждый запрос несёт всё нужное (например, токен)"
    - "У API нет базы данных"
    - "API не меняет данные"
  answer: 0
- q: Чем path-параметр отличается от query-параметра?
  options:
    - "Path идентифицирует ресурс (/orders/42), query уточняет выборку (?page=0)"
    - "Ничем"
    - "Query-параметры нельзя использовать в GET"
  answer: 0
- q: Как проверить пагинацию на баг потери элементов?
  options:
    - "Сложить размеры всех страниц и сравнить с totalElements"
    - "Проверить только первую страницу"
    - "Проверить код ответа 200"
  answer: 0
- q: Что такое OpenAPI?
  options:
    - "Стандарт описания REST API — контракт для разработки и тестов"
    - "Бесплатный API"
    - "Библиотека для тестов"
  answer: 0
```
